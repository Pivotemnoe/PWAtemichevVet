# Диагностика сохранения публичного разбора

Дата: 12 сентября 2026. Статус: реализовано и проверено локально; не опубликовано.

## Что изменено

- Клиент различает загрузку питомцев, подготовку, отправку сохранения и проверку ответа.
- `check.save_failed` получает безопасные `stage`, `http_status`, `error_code`, `attempt_id`; статус события — `error`. Текст исключения и медицинское содержимое в эти поля не копируются.
- `X-Tvv-Save-Attempt` связывает запрос с клиентским идентификатором сохранения; повтор использует тот же ключ идемпотентности.
- Сервер пишет `check.preview_save_rejected` для отказов этого endpoint, включая авторизацию, валидацию, rate limit и необработанное исключение. Для 422 — только допустимые имена полей и типы нарушений, без значений.
- Админка → Воронка: раздельные категории незавершённых сохранений и последние 80 клиентских/серверных диагностических записей.
- Подтверждённое сервером сохранение больше не превращается в ложную ошибку при последующем сбое отрисовки.
- Версия кеша приложения: `20260923-save-diagnostics-2`. Миграция БД не нужна.

## Границы интерпретации

Счётчики относятся к сессиям, не к людям. Авторизация сопоставляется внутри той же сессии, включая вход на `/app` и уже авторизованного пользователя. Успешное сохранение исключает сессию из незавершённых. Отсутствие события входа не доказывает уход. Старые ошибки без подробностей отображаются как `unknown`; точная причина ранее наблюдавшегося production-сбоя не восстановлена.

HTTP 0 означает отсутствие полученного ответа. Две записи client/server могут описывать одну попытку. Серверные диагностические записи включают технические запросы, но не прибавляются к продуктовым счётчикам. Клиентская телеметрия остаётся best effort.

## Проверка и выпуск

`make check`: 90 API-тестов, 4 теста мониторинга, frontend attribution, save-flow, отрисовка админки и синтаксические проверки. ASGI-тесты используют временную БД, без внешнего сервера: 401/404/422/429/500, приватность, безопасное описание нарушения формата, повтор без дубликата. Production-записи не создавались.

Остаётся выпустить backend и frontend согласованно, проверить новый кеш и диагностику в админке. Контролируемый production-тест, если будет разрешён, должен использовать служебную сессию и синтетические данные. Не считать локальные тесты подтверждением публикации или устранения неизвестной причины прежнего отказа.
