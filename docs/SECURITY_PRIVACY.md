# Security And Privacy Notes

Дата: 2026-06-03

TemichevVet PWA хранит персональные данные владельцев и данные о питомцах. Проект нельзя разворачивать как обычную статическую витрину без защищённого backend-слоя.

## Что хранится

- Пользователь: email, имя из внешнего провайдера, внешние account-id MAX/Telegram.
- Сессии: только hash токена, сам bearer-токен в базе не хранится.
- Питомцы: кличка, тип, порода, пол, дата рождения, вес.
- События питомца: история, наблюдения, напоминания, обращения по состоянию.
- Обратная связь: сообщения пользователя команде проекта.
- LLM-разборы: текст жалобы, ответ сервиса, уровень срочности, модель и usage-токены.

## Текущие правила доступа

1. Все API личного кабинета требуют `Authorization: Bearer ...`.
2. Сессии проверяются по HMAC-hash токена.
3. API не доверяет `pet_id` и `reminder_id` с фронта.
4. Для каждого действия сервер проверяет владельца:
   - карточка питомца;
   - история питомца;
   - наблюдения;
   - вес;
   - напоминания;
   - триаж с привязкой к питомцу.
5. API-ответы не кешируются service worker. PWA кеширует только shell и публичные картинки.

## Единый вход через Telegram

- PWA создаёт короткоживущий `state` и сохраняет только hash/служебную запись в backend-базе.
- Пользователь открывает рабочий Telegram-бот по deep-link `/start web_auth_<state>`.
- Telegram-бот подтверждает вход только серверным запросом на PWA API с общим секретом `PWA_TELEGRAM_AUTH_SECRET` / `TELEGRAM_AUTH_SECRET`.
- Секрет не попадает во frontend и не передаётся пользователю.
- После подтверждения PWA связывает `external_accounts.provider='telegram'` и Telegram user ID с PWA-пользователем.
- Если пользователь уже вошёл в PWA, Telegram/MAX подключается только к текущему кабинету через раздел «Способы входа».
- Один внешний Telegram/MAX ID нельзя тихо перепривязать к другому кабинету.
- Если Telegram подключён, PWA может читать и списывать квоту из Telegram `bot.db` по связанному Telegram ID.
- Если Plus будет выдан в PWA и Telegram уже подключён, PWA может серверно отразить этот платный тариф в Telegram `bot.db`.
- Фронт не сообщает тариф сам: источник подписки определяется только сервером.
- Синхронизацию питомцев нужно делать отдельным серверным этапом, без клиентского доверия.

## LLM И OpenAI

- `OPENAI_API_KEY` хранится только в server-side `.env`.
- Ключ OpenAI никогда не передаётся во frontend, service worker или API `/api/config`.
- Красные симптомы срабатывают до LLM и не списывают квоту.
- Если LLM недоступен, PWA возвращает ошибку и откатывает списание квоты.
- В логах нельзя выводить OpenAI-ключ, полный `.env` или платежные секреты.

## Вход по email

- Email-вход работает через одноразовый код сроком на 10 минут.
- В production код нельзя показывать во frontend или логах.
- Если SMTP не настроен, API должно возвращать ошибку `email_not_configured`, а не делать вид, что письмо отправлено.
- Для рабочего email-входа нужны доменная почта или SMTP-провайдер, `SMTP_HOST`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM_EMAIL`.

## Что нельзя делать

- Нельзя отдавать чужие записи по ID, даже если пользователь угадал URL.
- Нельзя хранить реальные access-токены в базе в открытом виде.
- Нельзя выводить секреты MAX, Telegram, YooKassa или SMTP во фронт.
- Нельзя активировать платный тариф на клиенте. Выдача Plus должна быть только после серверной проверки платежа.
- Нельзя использовать обратную связь как медицинский канал.

## SQLite Сейчас

Для MVP допустим SQLite:

- мало пользователей;
- один VPS;
- простая эксплуатация;
- быстрый backup файла `pwa.db`.

Обязательные правила:

- регулярный backup `pwa.db`;
- права на `.env` и `pwa.db` только для пользователя сервиса;
- HTTPS перед публичным использованием;
- отдельный systemd-сервис от Telegram-бота.

## PostgreSQL Далее

Переходить на PostgreSQL нужно до активного роста, когда появятся:

- много пользователей и параллельных записей;
- полноценные платежи в вебе;
- админка PWA;
- расширенная аналитика;
- отдельные роли доступа;
- юридически значимые выгрузки/удаления данных.

Рекомендуемая схема миграции:

1. Сохранить текущий API-контракт.
2. Вынести SQL из `app/db.py` в слой репозиториев.
3. Добавить миграции Alembic.
4. Перенести таблицы `users`, `external_accounts`, `sessions`, `pets`, `pet_history`, `pet_observations`, `pet_measurements`, `reminders`, `triage_logs`, `feedback`.
5. Проверить ownership-тесты на PostgreSQL.

## Перед Публичным Запуском

- Проверить HTTPS и HSTS.
- Настроить backup базы.
- Настроить SMTP с доменной почтой.
- Добавить rate-limit на email-коды и auth endpoints.
- Добавить логи попыток доступа к чужим ID.
- Добавить политику хранения и удаления данных пользователя.
- Подключить платежи только через серверную проверку YooKassa.
